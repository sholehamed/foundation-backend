# FR-13B-3 — in-person temporary password and compulsory first password change

Date: 2026-11-09. Backend [FR-13 #70](https://github.com/sholehamed/foundation-backend/issues/70), specific [#76](https://github.com/sholehamed/foundation-backend/issues/76). Depends on merged FR-13B-1/2. **Code is not deployment**.

## Decision: no normal login, JWT, or dashboard before the password has changed

This is a parallel onboarding method, not a replacement for email invitations. Reuse the existing **inactive** Tenant member created by the Owner; require a separate one-time initial-credential issuance action. Do not set a shared default password, activate an unverified employee, modify the ordinary login flow to issue an unrestricted "mustChangePassword" access token, or rely on an Angular-only redirect.

1. Active local Tenant Owner with writable home scope, `TENANT.MEMBERS.READ` and independently reviewed `TENANT.MEMBERS.ISSUE-TEMP-PASSWORD` ACTION invokes authenticated `POST /api/tenant/workspace/members/{id}/temporary-password`. Backend requires `Identity:TenantFirstLogin:Enabled=true` and HTTPS. SQL guards active explicit Permission/Module/Resource, exactly one matching ACTION UI link, no direct deny, local Owner, inactive non-Owner target. `TenantId`, owner, username, password and privilege cannot be supplied in the body.
2. Generates 24 cryptographically random characters from a no-confusing-character alphabet, grouped as 4×6, about 140 bits of entropy. Returns `{temporaryPassword,expiresAtUtc}` **once** to the Owner over HTTPS with `Cache-Control:no-store`; no GET retrieve endpoint. Owner handles it **in person after identity verification**. No shared default. No email/SMS. DO NOT enable response body, APM, WAF or proxy payload logging for the endpoint.
3. SQL Server SERIALIZABLE transaction stores **only PasswordHasher hash** in `TenantMemberTemporaryCredentials` for up to **60 minutes** (limited to 5 failed verifications), revokes previous temporary credentials, password-change challenges and outstanding email invitation links, and appends `temp_issued` to existing append-only TenantMemberLifecycleAuditEntries. No plaintext/password in audit or database.
4. Staff selects **First-time login** at `/auth/login` and opens `/auth/first-login` (not regular OAuth login). Anonymous `POST /api/public/tenant-first-login/start` with `{tenantSlug,userName,temporaryPassword}` is enabled only on exact HTTPS `{tenantSlug}.{Tenant:WorkspaceBaseDomain}`; server derives tenant ID from slug, verifies inactive local User and valid unrevoked hash against limited attempts. 5 request/min/IP, plus 5 invalid password attempts per issued credential. Generic 401 for unknown/expired/wrong credential. An accepted credential creates a **10-minute high-entropy single-use password-change-only challenge**; hash is stored in `TenantMemberFirstLoginChallenges`. Response `{challenge,expiresAtUtc,requiresPasswordChange:true}` is only in transient browser memory, **never a JWT/access token or authenticated session**.
5. Staff sets a new permanent password using anonymous `POST /api/public/tenant-first-login/complete` with `{tenantSlug,challenge,newPassword}`, same exact HTTPS host and throttle. Server validates 15–128 chars, no control characters, cannot include username or equal temporary password, and blocks a few trivially common passwords (later augment with credential breach screening before broader release). Under one SERIALIZABLE SQL transaction it checks the challenge, active tenant, unused/unexpired source credential, inactive non-Owner target, sets a hashed permanent password, `IsActive=true`, rotates security/concurrency stamps, consumes credential and challenge, revokes outstanding email invitation, appends `temp_activated` audit, and commits all-or-nothing.
6. **No session/JWT from either step.** Response is only `{passwordChanged:true,requiresRelogin:true}`. Angular clears both input passwords and challenge, shows success and navigates to ordinary login. A completely fresh normal authentication with the permanent password is required. Existing `UserCredentialAuthenticator` already refuses users with `IsActive=false`.
7. Owner may reissue the credential after in-person identity re-verification. All prior unused credentials and challenges are invalidated. Credentials for System, Owner, active staff or another Tenant are never issuable. Creating an inactive member does **not** implicitly send/reveal a temp password; email invitation remains an independent Owner-controlled action.

## Database / compatibility

- Migration `20261109030000_tenantmemberfirstlogin` adds `TenantMemberTemporaryCredentials` (TenantId, TargetUserId, Owner, password hash, expiry, attempts, used/revoked timestamps) and `TenantMemberFirstLoginChallenges` (TenantId, target, credential FK, SHA-256 of random challenge, expiry, used/revoked timestamps). SQL Server only.
- Existing Tenant feature catalog increases from 11 to **12** explicit definitions. An operator must separately review Registry Preview and approve Apply; it does not create grants. New action denies when catalog absent or unapproved, and independently checks live Owner permissions.
- Backend toggle `Identity:TenantFirstLogin:Enabled` is **false unless explicitly set true**. Angular first-login UI must be deployed with a corresponding default-OFF feature toggle and **same-origin HTTPS** API. Normal BFF/Cookie pilot, email invitation configuration and production permissions remain unchanged.
- Audit records only target IDs, actor IDs and event type. SQL append-only trigger and User update + audit in one transaction. No token, password, email or personally sensitive payload in audit.
- Current throttling is process-local; production multi-node deployment needs distributed/global gateway throttling, IP reputation, per-user backoff monitoring and credential leak redaction in access/security logs. TLS proxy trusted forwarding and HTTPS hosts must be verified in Staging. This flow cannot establish which human physically received the one-time credential: Owner must verify identity at handoff; do not provide it on public screens.

## Test and rollout gate

Real disposable SQL tests cover initial inactive user, single-use reveal and challenge, wrong password cap, expiry, reissue, direct-deny, foreign/Owner target exclusion, atomic audit rollback, password hash/stamp rotation and no automatic role grants. Angular component/utility tests verify default disabled, same-origin cookie-free POST, no token persistence, password clearing and explicit re-login. Full HTTPS browser multi-account test and operator-approved migrations/Registry Apply/grants on isolated staging remain separate acceptance.

**No automatic migration, Production flag enablement, grants or deployment is authorized by this PR.**
