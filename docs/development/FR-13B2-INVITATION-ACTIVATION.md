# FR-13B-2 — secure invitation + activation (initial backend slice)

Date: 2026-11-09. Parent [FR-13 #70](https://github.com/sholehamed/foundation-backend/issues/70), acceptance [FR-13B-2 #74](https://github.com/sholehamed/foundation-backend/issues/74). Based on Backend FR-13B-1 commit `7d42c754559cc9d487cc2ed0a163f24742b11acd` and Frontend baseline `d0adb3e2ee761992b85f10a829edbc90509610f5`.

## Contract

1. System Administrator explicitly reviews and (under a separate, default-OFF opt-in) applies the new, code-owned `TENANT.MEMBERS.INVITE` ACTION: `tenant.workspace.members.invite`. Tenant catalog increases 10 -> 11. The catalog sync **never** grants a permission. Issue endpoint is inaccessible unless exact, unique, active Permission/Resource/Module/ACTION link is registered, and the actor is a live local Tenant Owner with `TENANT.MEMBERS.READ`, explicit `TENANT.MEMBERS.INVITE`, writable home Tenant and no direct deny.
2. Authenticated `POST /api/tenant/workspace/members/{id}/invitations` accepts no TenantId, role, password or arbitrary recipient. Target is a *local, inactive and unconfirmed* ordinary Tenant member; self/Owner/System/foreign/active targets cannot be invited. Rate limit 5/min per authenticated principal. If SMTP is unconfigured, fails 503 before making any token/audit records.
3. A 32-byte CSPRNG invitation token is sent **only** to the target User.Email through a separately configured TLS-authenticated SMTP relay. A SHA-256 digest is the only token representation in SQL (`TenantMemberInvitations.TokenHash`, 32 bytes, unique index). 30-minute lifetime; an Owner resend revokes previous active/pending invitations. There is no token in the Owner's HTTP response, logs, database audit, localStorage or URL GET requests.
4. SMTP message sends link `https://{tenantSlug}.{Tenant:WorkspaceBaseDomain}/auth/activate#token={HEX64}`; the fragment is not sent to the origin as part of the GET. **The Angular page must capture the fragment only in memory and immediately remove it from the browser URL**, then POST over HTTPS. The customer-facing route exists only when the companion Frontend PR lands.
5. Issuance + immutable audit commit atomically under SQL Server SERIALIZABLE transaction. SMTP submission then happens *after* commit. An invitation cannot activate until SMTP submission status is written and audited in a separate atomic SQL transaction. If SMTP or persistence fails, pending tokens are **not redeemable** (the mail may be accepted but a crash before recording submission invalidates it; Owner can resend). HTTP status `submitted` means accepted by configured relay, **not inbox delivered**.
6. Anonymous `POST /api/public/tenant-invitations/activate` body `{tenantSlug,token,password}`, 5/min per IP. No account cookie or identity required. HTTPS required outside Development loopback. Requires matching active Tenant slug, active submission, unexpired/unrevoked/unconsumed unique hashed token, inactive/unconfirmed local target and no Owner link. Password must be 12..128 characters including uppercase, lowercase, digit and nonalphanumeric; the existing ASP.NET Identity PasswordHasher securely hashes it. SQL SERIALIZABLE transaction updates password/EmailConfirmed/IsActive/stamps, marks single-use token consumed and appends `invite_activated` audit; any error rolls everything back. Response has only `activated:true`, never tokens or password. Invalid/replayed/expired/wrong tenant returns the same 400 error.
7. The login pipeline still independently validates `IsActive` and Tenant scope; activating an account gives **no roles/grants**. Owner must explicitly assign a non-Owner local role afterwards.

## Storage / deployment gate

- New migration `20261109020000_tenantmemberinvitation` adds `TenantMemberInvitations`, containing only SHA-256 digest, TenantId, UserId, issuing Owner, issue/expiry/submission/use/revocation timestamps. No plaintext tokens or passwords. Existing append-only `TenantMemberLifecycleAuditEntries` ledger receives events `invite_issued`, `invite_submitted`, `invite_failed`, `invite_activated`. This is not a cryptographically tamper-proof ledger.
- Default `Identity:TenantInvitations:Enabled=false` (absent/false), with SMTP `Host`, `Port` (default 587), `From`, `User`, `Password`; TLS negotiation required and normal certificate verification retained. Secrets must be provisioned via secret manager/environment, **never committed into appsettings or a repository**.
- Actual Staging DNS/HTTPS/frontend, isolated SQL migrations, Registry Preview/Apply and grants require separate operator approval; **no Production DB is touched by this PR**. Production BFF and UI pilot flags stay OFF.
- The current single-instance in-memory RateLimiter is a first boundary, not multi-node global limiting: rollout must provide gateway/distributed throttling and monitoring, protect SMTP quotas and verify anti-enumeration before Production.
- Do not treat `submitted` as guaranteed mailbox delivery. An authenticated relay does not verify ownership of email until the actual link is redeemed. The signed invitation token is the confirmation factor.

## Validation / remaining work

- Disposable real SQL tests: token hash only, no Owner token leakage, expiry/replay/wrong-tenant refusal, foreign and Owner denial, no-op/unconfigured delivery, audit transaction failure rollback and live login activation. Test endpoints over real HTTP before Production.
- Frontend companion: add server-capability-gated Invite action for inactive members, immediate permission recheck, transient token/password activation form on dedicated public tenant route, clear fragment early and never store token in persistent storage or Angular router logs.
- Run true Chromium/HTTPS two-user lifecycle (invite -> activation -> role grant -> staff login -> menu -> revoke -> fresh-session 403), plus tenant isolation, CSRF/cookie behavior and deployment staging evidence.
- No automatic seed/grant of the new ACTION: manual approved catalog Apply is still necessary and will intentionally invalidate previous reviewed preview fingerprints.

**Security caveat:** SMTP relay credentials and domain/TLS proxy configuration are not available in this repository. A passing CI with a test double proves core state transitions, not that a real email was delivered in Staging or Production.
